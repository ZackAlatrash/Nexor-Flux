#   ISOWEEK  2026-01-01 -> 2026-W01
#   ISOWEEK  2027-01-03 -> 2026-W53  (early-January date lands in the previous week-based year)
#
# --- Behaviour a naive reimplementation will get wrong ----------------------------------
# 1. java.util.Formatter does NOT round the exact binary value. It rounds HALF_UP over the
#    SHORTEST decimal representation of the double, inspecting only the digit just past the
#    requested precision. Hence, against C printf intuition:
#      FMT2  1.005  -> 1.01   (C printf gives 1.00; the double is below 1.005)
#      FMT2  2.675  -> 2.68   (C printf gives 2.67)
#      FMT2  0.145  -> 0.15
#    but at one decimal the next shortest-repr digit is '4', so it rounds DOWN:
#      FMT1  0.145  -> 0.1    (NOT 0.2)
#    A port that formats via BigDecimal-of-the-exact-double, or that uses Kotlin's
#    toDouble/roundToInt chain, will disagree on these rows.
# 2. fmt() preserves negative zero as a literal minus sign:
#      FMT1  -0.0 -> -0.0 ;  -0.049 -> -0.0 ;  -0.001 -> -0.0
#      FMT2  -0.0 -> -0.00 ; FMT0 -0.0 -> -0 ;  FMT0 -0.25 -> -0
#    Only signed1() and bucket() normalise it away.
# 3. roundToInt() rounds halves toward POSITIVE INFINITY, unlike Formatter's HALF_UP. The two
#    live side by side in this file, so the sign asymmetry is real and must be preserved:
#      PCT     0.5  -> 1%    but  -0.5  -> 0%
#      BUCKET(step=0.1)  0.05 -> 0.10  but -0.05 -> 0.00
#      BUCKET(step=0.1)  0.25 -> 0.30  but -0.25 -> -0.20
#      BUCKETINT(step=5)   3  -> 5     and   -3  -> -5   (roundToInt(-0.6) = -1)
#      BUCKETINT(step=5)   7  -> 5     and   -7  -> -5
# 4. bucket() applies the -0.0 -> 0.0 normalisation AFTER bucketing, so no bucket row ever
#    prints a signed zero, even where fmt() alone would.
# 5. ISO week-based year != calendar year at both boundaries:
#      2021-01-01 -> 2020-W53 ; 2025-12-29 -> 2026-W01 ; 2026-12-28 and 2026-12-31 -> 2026-W53
#    2026 and 2020 are 53-week years. Week numbers are zero-padded to two digits, year to four.
#

# WHY: the first :shared implementation of formatFixed() bailed out with `check(...)` when
# Double.toString() returned scientific notation. Kotlin emits E-notation for |v| < 1e-3 and
# |v| >= 1e7, and TrendCalculator.trendPerWeek (an OLS slope) produces residues like 1.66E-15 on a
# flat series - exactly the values BodyDetectors/TrainingDetectors format inside their
# "flat band" branches. On the JVM those format cleanly as "0.00"; the :shared version threw, the
# throw was swallowed by CoachDigestCoordinator's runCatching, and the whole digest staged no
# signal that day. These rows are the ground truth that formatFixed() must reproduce instead.
#
# The `=== TOSTRING ===` section records which inputs actually take the E-notation path (0.001 does
# not - it is kept as the boundary control).
#
# Large values were the suspected risk (Java's %f printing the exact binary value where the
# shortest representation is shorter) and turned out NOT to be one. java.util.Formatter pads the
# same shortest-representation digits for %f. Cross-checked on the same JDK 21 against a Java port
# of the shared expansion, over {1.0E20, 1.0E23, 1.23E22, 1.0E16, Double.MAX_VALUE, Double.MIN_VALUE,
# 1.0E-7, 1.66E-15, 3.14159E30, 9.87654321E45, 1.0E7, 1.23E8, 6.02214076E23, 2.5E-11, 7.77E-5} x
# {0,1,2} decimals: 0 divergences. Note %.0f of 1.0E23 is 100000000000000000000000, NOT the exact
# binary 99999999999999991611392 - so matching Java means NOT using the exact value.
#
# The last BUCKET row is not a formatter quirk: (1e20 / 0.1).roundToInt() saturates at
# Int.MAX_VALUE, so bucket() formats 2147483647 * 0.1. Captured as-is, quirk and all.
